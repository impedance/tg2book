# Интеграция Юзербота для Пересылки Сообщений

План создания юзербота, который будет пересылать новые сообщения из заданных каналов в существующего Telegram-бота для конвертации в EPUB.

## User Review Required
> [!IMPORTANT]
> Для работы юзербота от вашего имени потребуются **API_ID** и **API_HASH**.
> Вам будет необходимо получить их на сайте `my.telegram.org` и добавить в файл конфигурации `.env`.
> **ВАЖНО для Docker**: Так как бот запускается через Docker, интерактивный ввод при старте основного бота недоступен. Потребуется единоразово запустить вспомогательный скрипт `login_userbot.py` для создания файла сессии `userbot.session`, который затем будет смонтирован в контейнер.

## Архитектурный Анализ и Оптимизация
> [!TIP]
> Учитывая, что ваш проект оптимизируется для работы на слабом VDS (512МБ RAM), запускать два отдельных процесса Python (Бот и Юзербот) — неэффективно.
> **Решение**: Мы объединим бота и юзербота в **один процесс**, работающий на общем асинхронном цикле (`asyncio loop`). Pyrogram Client будет запускаться как фоновая `asyncio.Task` параллельно с основным циклом `python-telegram-bot`. Это сэкономит около 40-60МБ оперативной памяти.

## Принципы Антихрупкости
> [!WARNING]
> Для предотвращения падений из-за исчерпания памяти (OOM) при массовой пересылке сообщений, между перехватчиком Pyrogram и генератором EPUB будет внедрена **асинхронная очередь (`asyncio.Queue`)** с ограничением одновременно обрабатываемых задач (конкурентностью = 1). Это сгладит пиковые нагрузки.
> **Known Limitation**: Использование in-memory очереди (`asyncio.Queue`) означает, что при перезапуске контейнера или падении процесса сообщения, находящиеся в очереди, будут потеряны. Для MVP это приемлемый компромисс ради экономии памяти.

## Proposed Changes

### [MODIFY] [bot.py](file:///home/spec/work/tg2book/bot.py)
1.  **Интеграция Pyrogram**: Добавление инициализации клиента Pyrogram. Запуск и остановка клиента будут привязаны к хукам жизненного цикла `python-telegram-bot` (`post_init` и `post_stop`), что обеспечит корректную работу обоих клиентов в одном Event Loop. Перехват системных сигналов в Pyrogram будет отключен.
2.  **Команды управления**:
    - `/add_channel <username>` — добавляет канал в БД и сразу начинает его отслеживать.
    - `/del_channel <username>` — удаляет из БД.
    - `/list_channels` — список текущих каналов.
3.  **Безопасность**: Добавление проверки `ADMIN_ID` из `.env`, чтобы управлять каналами могли только вы.
4.  **Очередь обработки**: Замена существующего механизма `asyncio.Semaphore(1)` на паттерн Producer-Consumer (с `asyncio.Queue` и выделенным фоновым таском-воркером) для надежной маршрутизации и ограничения одновременных конвертаций. **Важно**: Результаты конвертации для сообщений из каналов отправляются напрямую на `ADMIN_ID` через метод `bot.send_document(chat_id=ADMIN_ID, ...)`.

### [NEW] login_userbot.py
Вспомогательный скрипт для первичной авторизации юзербота. Запускается вручную один раз, запрашивает телефон и код, после чего генерирует файл сессии `data/userbot.session`.

### [NEW] userbot_db.sqlite
Вместо хрупкого `channels.json` будет использоваться легковесная база SQLite3 с асинхронным драйвером **`aiosqlite`**. Использование синхронного `sqlite3` недопустимо, так как это заблокирует Event Loop. Это обеспечит транзакционность, атомарность операций и нулевой риск повреждения списка каналов.

### [MODIFY] [.env](file:///home/spec/work/tg2book/.env)
Добавление новых переменных:
- `API_ID`, `API_HASH` (для юзербота).
- `ADMIN_ID` (ваш Telegram ID для доступа к командам управления и получения готовых EPUB файлов).

### [MODIFY] [requirements.txt](file:///home/spec/work/tg2book/requirements.txt)
Добавление `pyrogram`, `tgcrypto` и `aiosqlite`.

### [MODIFY] [docker-compose.yml](file:///home/spec/work/tg2book/docker-compose.yml)

- Будет монтироваться директория `./data:/app/data` для хранения базы данных и сессии. Пути в коде обновятся соответственно.

## Verification Plan

### Automated Tests
* Будут написаны юнит/интеграционные тесты с мокированием `pyrogram.Client` и `asyncio.Queue` для проверки бизнес-логики бота (добавление каналов в БД, маршрутизация сообщений в очередь) без реального подключения к серверам Telegram.

### Manual Verification
1.  **Сценарий авторизации**:
    * Запустить `python login_userbot.py` локально или внутри интерактивного контейнера.
    * Убедиться, что скрипт запрашивает номер телефона и код из Telegram.
    * Убедиться, что успешно сгенерирован файл `data/userbot.session`.
    * Запустить бота через Docker Compose и убедиться, что он подхватывает сессию и не запрашивает авторизацию снова.
2.  **Сценарий пересылки и ограничения ресурсов (Crash Test)**:
    * Отправить тестовые сообщения в отслеживаемый канал (сразу 5-10 штук).
    * Убедиться с помощью `docker stats` (или `htop`), что пиковое потребление памяти ограничено благодаря `asyncio.Queue` и выделенному воркеру, и сообщения конвертируются последовательно, одно за другим, не вызывая превышения лимитов VDS.
3.  **End-to-End**: Пост в канале -> Перехват юзерботом -> Помещение в асинхронную очередь -> Обработка ботом -> EPUB отправлен админу напрямую и успешно загружен в Dropbox (если настроен).
4.  **Проверка надежности состояния SQLite**: Завершить работу бота принудительно во время записи (нажав Ctrl+C). Убедиться, что после перезапуска скрипта список отслеживаемых каналов не повредился и остался корректным.
