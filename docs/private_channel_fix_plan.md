# План фикса отслеживания приватных каналов по инвайт-ссылкам

В этом документе описан подробный план исправления логики работы бота для корректного перехвата сообщений из приватных каналов, добавленных через инвайт-ссылки.

## 1. Описание проблемы
Текущая логика работы команды `/add_channel <target>` просто сохраняет переданную пользователем строку (юзернейм или инвайт-ссылку) в базу данных `userbot_db.sqlite`.
Когда юзербот перехватывает сообщение из канала, он проверяет:
1. `chat.username`
2. `chat.id`

У приватных каналов `chat.username` всегда равен `None`. А `chat.id` имеет числовой вид (например, `-1001234567890`). Строка инвайт-ссылки (например, `https://t.me/+AbCdEfGhIjKlMnOp`) при этом нигде не фигурирует в `pyro_message`, из-за чего сопоставление проваливается, и сообщение игнорируется.

## 2. Архитектурный подход к решению
Поскольку бот и юзербот работают в **едином процессе** (асинхронном Event Loop), мы можем использовать клиент Pyrogram напрямую в функции-обработчике `add_channel` (из пакета `python-telegram-bot`). 

Суть фикса: при вызове `/add_channel` мы не будем слепо сохранять ссылку в БД. Вместо этого мы попросим Pyrogram "разрешить" (resolve) эту ссылку или юзернейм в каноничный числовой **Chat ID** с помощью метода `await self._userbot.get_chat(target)`. В базу данных мы будем сохранять именно этот числовой ID.

## 3. Предлагаемые изменения (Proposed Changes)

### bot.py
1. **Обновление команды `/add_channel`**:
   * В методе `add_channel` получить сырой аргумент пользователя `target = context.args[0]`.
   * Перед сохранением в БД проверить, запущен ли `self._userbot`.
   * Если запущен, попробовать выполнить `chat = await self._userbot.get_chat(target)`.
   * Если успешно — получить `chat.id` (строкой) и `chat.title`.
   * Сохранить в БД именно `str(chat.id)`, а не переданную ссылку.
   * Отправить успешный ответ пользователю: `✅ Канал "{chat.title}" (ID: {chat.id}) добавлен в список отслеживания.`.
   * **Fallback (резервный путь)**: Если `get_chat` выбрасывает исключение (например, юзербот еще не вступил в канал, или ссылка невалидна), залогировать предупреждение и сохранить оригинальный ввод `target` (как это делается сейчас), предупредив пользователя сообщением: `⚠️ Не удалось автоматически определить ID канала. Ссылка сохранена "как есть".`.
2. **Обновление команды `/del_channel`**:
   * Опционально реализовать аналогичный механизм резолва, чтобы позволить пользователю удалять канал по его ссылке или юзернейму, который будет переводиться в ID перед удалением из БД. Либо просто оставить удаление по точному совпадению (так как `/list_channels` будет выводить ID).
3. **Обновление сообщения `/list_channels`**:
   * Учитывая, что в БД теперь будут храниться и числовые ID, при выводе списка мы будем выводить их "как есть" `• ID: -10012345678`, чтобы пользователь понимал, что именно удалять при необходимости.

## 4. План проверки (Verification Plan)

### Ручная проверка (Manual Verification)
1. **Сценарий 1 (Публичный канал / Юзернейм):**
   * Выполнить `/add_channel @durov`.
   * Бот должен ответить: `✅ Канал "Durov's Channel" (ID: -1001222851163) добавлен...`
   * Выполнить `/list_channels`. Убедиться, что в списке отображается ID.
2. **Сценарий 2 (Приватный канал / Инвайт-ссылка):**
   * Вступить юзерботом в тестовый приватный канал.
   * Выполнить основным ботом команду `/add_channel <инвайт-ссылка>`.
   * Бот должен успешно определить название и ID канала: `✅ Канал "Тайный канал" (ID: -100987654321) добавлен...`.
   * Написать тестовое сообщение в этот приватный канал.
   * Убедиться, что сообщение перехвачено юзерботом, поставлено в очередь и отправлено админу в виде EPUB файла (строгое совпадение по числовому ID).
3. **Сценарий 3 (Невалидный ввод / Ограничения):**
   * Выполнить `/add_channel https://t.me/fake_impossible_link`.
   * Бот должен ответить: `⚠️ Не удалось автоматически определить ID канала...`. В БД должна сохраниться сырая ссылка в качестве резервного варианта.
