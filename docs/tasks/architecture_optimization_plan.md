# План архитектурной оптимизации проекта для VDS (ОЗУ, CPU, I/O)

## Описание
Данный план направлен на глубокую оптимизацию бота для работы на слабых VDS. Реализация разделена на три ключевых направления: оптимизация потребления оперативной памяти (RAM) путем перехода на моно-фреймворк, предотвращение блокировки Event Loop (CPU) за счет изоляции ресурсоемких задач, и ускорение работы с диском (I/O) через настройку SQLite.

---

## 1. Избавление от "двуглавой" архитектуры (Оптимизация ОЗУ - RAM)

**Цель:** Оставить в проекте только один Telegram-фреймворк (`Pyrogram`), избавившись от `python-telegram-bot` (PTB), чтобы снизить потребление памяти на 30-40%.

### Задачи:
1.  **[ ] Замена зависимостей:** Удалить `python-telegram-bot` из `requirements.txt` / `Pipfile`.
2.  **[ ] Перенос команд (bot.py):**
    *   Переписать обработчики команд `/start`, `/help`, `/add_channel`, `/del_channel`, `/list_channels` с синтаксиса PTB на синтаксис Pyrogram.
    *   *Пример:* `@app.on_message(filters.command("start") & filters.private)`
3.  **[ ] Адаптация проверки прав (Admin Check):**
    *   Создать кастомный фильтр Pyrogram `is_admin`, который проверяет `message.from_user.id == settings.ADMIN_ID`.
    *   Применить его к админским командам: `@app.on_message(filters.command("add_channel") & is_admin)`.
4.  **[ ] Инициализация единого клиента:**
    *   Вместо `ApplicationBuilder` (PTB) и отдельного `PyrogramClient`, создать единый инстанс `app = Client(...)`.
    *   Он должен использовать `BOT_TOKEN` для работы команд и `USERBOT_SESSION` для прослушивания каналов (или два связанных клиента внутри одного Event Loop, если архитектура Pyrogram того требует, но код должен быть консолидирован). *Важно изучить доку Pyrogram на предмет совмещения бота и юзербота в одном процессе.*
    *   *Уточнение:* Юзербот (сессия пользователя) читает каналы, а бот (по токену) общается с админом. Нужно запустить два инстанса `Client` (один как бот, другой как юзер) в одном `asyncio` цикле, используя общие фильтры и очередь. Это все равно легче, чем два разных фреймворка.
5.  **[ ] Адаптация обработки файлов (EPUB upload):**
    *   Переписать загрузку `.epub` файлов от пользователя через метод `client.download_media(message.document)`.

### 1.1 Black-Box Тесты (Антихрупкость):
*   **Тест 1 (Доступность команд):** Отправить `/help` от лица админа -> получить ожидаемый ответ. Отправить `/help` от лица чужого юзера -> получить ожидаемый ответ (или игнор, в зависимости от логики).
*   **Тест 2 (Права доступа):** Отправить `/add_channel @test` от чужого юзера -> команда проигнорирована или получен отказ. Отправить от админа -> канал добавлен.

## 2. Изоляция генерации EPUB от Event Loop (Оптимизация CPU)

**Цель:** Вынести тяжелую задачу сборки книги (парсинг, архивация) в пул потоков, чтобы основной цикл `asyncio` не блокировался и бот продолжал мгновенно отвечать на сообщения.

### Задачи:
1.  **[ ] Анализ `epub_service.py`:** Выявить синхронные (блокирующие) вызовы (файловые операции, создание ZIP/EPUB архива).
2.  **[ ] Обертка в ThreadPoolExecutor:**
    *   Создать функцию-обертку, например `async def process_text_to_epub_async(...)`.
    *   Использовать `loop.run_in_executor(None, generate_epub_sync, data)` или удобный `asyncio.to_thread(generate_epub_sync, data)` (если Python 3.9+).
3.  **[ ] Рефакторинг воркера:**
    *   В `_channel_worker` (или его аналоге на Pyrogram) убрать прямой `await` тяжелой функции в основном потоке, использовать обертку `to_thread`.
    *   *Обеспечение антихрупкости:* Убедиться, что исключения из потока (`Thread`) корректно перехватываются в основном цикле `try...except`, логируются, и воркер `processing_queue` завершает задачу (`task_done()`), не падая целиком.

### 2.1 Black-Box Тесты (Антихрупкость):
*   **Тест 3 (Неблокирующая работа):**
    1. Положить в очередь 5 огромных сообщений (симуляция довгого создания EPUB).
    2. Во время их фоновой обработки отправить боту команду `/start`.
    3. *Ожидание:* Бот должен ответить на `/start` мгновенно (<0.1 сек), не дожидаясь завершения сборки книг.

## 3. Включение WAL-режима для SQLite (Оптимизация I/O)

**Цель:** Ускорить работу с базой данных, уменьшить задержки при чтении/записи на медленных VDS дисках и предотвратить "database is locked" ошибки.

### Задачи:
1.  **[ ] Модификация инициализации БД (`userbot_db.py`):**
    *   Найти место подключения к базе (вероятно, используется `aiosqlite.connect(...)`).
    *   Сразу после коннекта выполнить `await db.execute("PRAGMA journal_mode=WAL;")`.
    *   Выполнить `await db.execute("PRAGMA synchronous=NORMAL;")`.
2.  **[ ] Управление соединениями:**
    *   *Обеспечение антихрупкости:* Тщательно проверить, чтобы все запросы использовали `async with aiosqlite.connect(...) as db:` для гарантированного закрытия соединений, чтобы не исчерпать пул и не оставить висящие lock-и. Идеально – вынести пул или глобальный объект БД, чтобы не открывать файл по 100 раз.

### 3.1 Black-Box Тесты (Антихрупкость):
*   **Тест 4 (Параллельная запись/чтение):**
    1. Запустить 10 конкурентных `asyncio.gather` тасок: половина постоянно вызывает `/add_channel`, вторая половина `/list_channels` или читает каналы при фильтрации.
    2. *Ожидание:* Ни один запрос не должен упасть с ошибкой "database is locked" (OperationalError).

## Порядок выполнения
1. Начать с **Этапа 3 (SQLite WAL)** — самые быстрые и безопасные изменения. 
2. Перейти к **Этапу 2 (Изоляция CPU)** — изменения локальны в одном сервисе и воркере.
3. Завершить **Этапом 1 (Переход на Pyrogram)** — самый объемный рефакторинг, требующий изменения структуры всего бота.
