# План: упаковать tg2book в Docker Compose (минимум действий — максимум эффекта)

## Цели
- Бот запускается в фоне и сам поднимается после перезагрузки ПК.
- Конфиг/секреты лежат на хосте и не попадают в образ.
- Логи удобно смотреть одной командой.
- Обновления делаются предсказуемо: правка кода → пересборка → быстрый рестарт.

## Контекст
- Целевая ОС: Ubuntu (VDS/локальная машина).

## Предпосылки
- Docker установлен.
- Запуск бота сейчас возможен через `python3 bot.py` при наличии переменных окружения (Telegram/Dropbox).
- Интернет нужен только при сборке (скачать зависимости).

---

## Минимальный набор файлов (MVP)
1) `Dockerfile`
2) `docker-compose.yml`
3) `.dockerignore`
4) (опционально) `.env` на хосте для `docker compose` (НЕ копировать в образ; добавить в `.dockerignore`)

---

## Шаги реализации (по порядку)

### 1) Определить конфигурацию и секреты
Составить список переменных окружения, которые нужны боту:
- `TELEGRAM_BOT_TOKEN`
- `DROPBOX_APP_KEY`
- `DROPBOX_APP_SECRET`
- `DROPBOX_REFRESH_TOKEN`

Принять решение, как хранить:
- **MVP:** `./.env` рядом с `docker-compose.yml` (просто и быстро).
- **Чуть безопаснее:** Docker secrets (если будете развивать дальше).

### 2) Подготовить `.dockerignore` (ускорение сборки + безопасность)
Добавить исключения, чтобы в образ не улетали мусор/секреты/артефакты:
- `.venv/`, `__pycache__/`, `.pytest_cache/`, `*.epub`, `bot.log`, `.env`, `.env.*`, `.git/` (по желанию)

Эффект: сборка быстрее, меньше риск случайно запечь секреты.

### 3) Написать `Dockerfile` (один сервис, один процесс)
Минимальные принципы:
- База: `python:3.11-slim` (или `3.12-slim`)
- Слой зависимостей отдельно от слоя кода для кеша:
  1) копируем `requirements.txt`
  2) `pip install -r requirements.txt`
  3) копируем остальной код
- `CMD ["python", "bot.py"]` (или `python3`)

Опционально (но полезно даже в MVP):
- Запуск не от root (создать пользователя).
- `PYTHONUNBUFFERED=1`, чтобы логи шли сразу.
- `init: true` в compose (или tini в образе), чтобы аккуратно обрабатывались сигналы/зомби-процессы.

### 4) Написать `docker-compose.yml` (автозапуск + удобные логи)
MVP-настройки:
- `build: .`
- `env_file: .env` (чтобы не дублировать переменные; файл остаётся на хосте)
- `restart: unless-stopped` (сам поднимется после ребута)
- (опционально) `volumes:` если хотите хранить логи/выходные файлы на хосте

Рекомендация по логам:
- **Самый удобный вариант:** направить логирование в `stdout/stderr` и смотреть через `docker compose logs -f` (для этого придётся поменять конфиг логирования в коде).
- **Если оставить как сейчас (лог в файл `bot.log`)**: либо смотреть файл внутри контейнера (`docker compose exec ... tail -f`), либо монтировать путь под `bot.log` на хост (потребует согласовать права).

### 5) Запуск и проверка
Команды (как “операционный ритуал”):
- Первый старт: `docker compose up -d --build`
- Смотреть логи: `docker compose logs -f`
- Проверить статус: `docker compose ps`

### 6) Обновления (как вы будете жить дальше)
Сценарии:
- Поменяли только код: `docker compose up -d --build` (обычно быстро, зависимости кешируются)
- Поменяли `requirements.txt`: та же команда, но сборка дольше (переустановка зависимостей)

### 7) Автозапуск при включении компьютера (что важно понимать)
`restart: unless-stopped` сработает **только если Docker Engine запускается вместе с системой**:
- Ubuntu: обычно достаточно `systemctl enable --now docker`

## Ожидаемые ресурсы (ориентиры для VDS 1 ГБ RAM / 1 vCPU)
- Idle (ждёт сообщения): CPU обычно <1%, RAM часто 60–150 МБ.
- Пики на генерации EPUB: CPU всплесками, RAM чаще 150–300 МБ; выше — если будут большие входные данные/картинки/параллельная обработка.
- Вывод: на 1 ГБ обычно ок, но важно ограничить параллелизм и поставить лимит памяти контейнера.

## Режимы “макс эффект” (опционально, но полезно)

### A) Healthcheck (чтобы видеть “жив ли бот”)
- Добавить `healthcheck` в compose (в идеале — простой endpoint/самопроверка, но для Telegram-бота часто достаточно “процесс жив”).
- Польза: быстро заметно, что контейнер в проблеме.

### B) Разделить dev/prod
- `docker-compose.yml` (prod): без монтирования кода, только образ.
- `docker-compose.override.yml` (dev): с bind-mount кода + быстрые итерации.

### C) Нормализовать логирование
- Перевести логгер на `stdout` (вместо `filename='bot.log'`) — тогда лог-стек Docker работает идеально.
- Если нужен файл — писать его дополнительно, но не вместо stdout.

### D) Ограничение ресурсов
- В `docker-compose.yml` можно задать лимиты CPU/RAM, чтобы бот не “съел” машину при проблемах (на Ubuntu это реально помогает при утечках/пиках).

### E) Параллелизм и контроль памяти (для маленьких VDS)
- Ограничить параллелизм обработки (очередь/семафор на 1 задачу), чтобы снизить риск OOM на тяжёлых сообщениях.
- В `docker-compose.yml` задать лимиты, чтобы контейнер не “съел” весь сервер: `mem_limit: 512m–768m`, CPU лимит — по желанию.
- Мониторинг: `docker stats` + алерты по памяти; логи через `docker compose logs -f`.

---

## Чеклист “готово”
- [ ] `docker compose up -d` поднимает бота без ручных действий.
- [ ] `docker compose logs -f` показывает нормальные логи (и ошибки видны).
- [ ] После перезагрузки ПК контейнер сам стартует.
- [ ] Секреты не попали в образ (нет `.env` в контексте сборки, есть `.dockerignore`).

---

## Быстрые команды оператора
- Старт/апдейт: `docker compose up -d --build`
- Логи: `docker compose logs -f --tail=200`
- Рестарт: `docker compose restart`
- Остановка: `docker compose down`
- “Зайти внутрь”: `docker compose exec tg2book sh`

---

## Риски/тонкие места (чтобы не удивиться)
- Если логирование сейчас пишет в `bot.log` с `filemode='w'`, при рестарте файл может перетираться (лучше stdout или append/ротация).
- Если будете монтировать файлы/папки (логи/epub) — нужны корректные права пользователя внутри контейнера.
- Dropbox refresh flow: все нужные переменные должны быть в окружении контейнера, иначе загрузка начнет падать.

## Разбиение на задачи для джунов (t1…)

### t1 — Подготовить `.dockerignore`
**Цель:** исключить секреты/мусор из контекста сборки.  
**Готово, если:** `.env` и `.env.*` не попадают в `docker build`, сборка не тащит `.venv/` и артефакты.

### t2 — Написать минимальный `Dockerfile`
**Цель:** собрать образ, который запускает `python bot.py`.  
**Готово, если:** `docker build .` проходит, контейнер стартует без интерактива.

### t3 — Написать `docker-compose.yml` для Ubuntu
**Цель:** сервис с автоперезапуском.  
**Состав:** `build`, `env_file`, `restart: unless-stopped`, (опционально) `init: true`.  
**Готово, если:** `docker compose up -d` поднимает сервис и он остаётся запущенным.

### t4 — Прописать лимиты ресурсов в compose (VDS 1 ГБ)
**Цель:** не допустить “съедания” всей памяти/CPU.  
**Рекомендация:** `mem_limit: 768m` (или `512m` если нужно жёстче), CPU лимит — опционально.  
**Готово, если:** `docker stats` показывает ограничения, при пиках контейнер не валит весь хост.

### t5 — Решить схему логов (stdout или файл)
**Вариант A (рекомендуется):** перевести логирование на `stdout/stderr`, смотреть через `docker compose logs -f`.  
**Готово, если:** логи доступны без “ручного захода” в контейнер и не теряются на рестарте.

### t6 — Ограничить параллелизм обработки в коде
**Цель:** снизить риск OOM на VDS 1 ГБ.  
**Реализация:** семафор/очередь на 1 активную “тяжёлую” задачу (генерация EPUB/обработка медиа).  
**Готово, если:** при одновременных сообщениях обработка становится последовательной и память не растёт скачком.

### t7 — Операционные команды и короткий runbook
**Цель:** чтобы любой мог обслуживать.  
**Состав:** старт/стоп/апдейт/логи/статус, типовые ошибки (нет токенов, нет сети, OOM).  
**Готово, если:** новый человек может поднять/перезапустить сервис по инструкции.
